# Task Overview

[English](task-overview.md) | [中文](task-overview.cn.md)

The standalone O4E TUI plugin displays the tasks **directly owned** by the current Session in the sidebar above the Todo area (`sidebar_content`, `order: 350`), grouped by Bash / subagents. Each group shows at most six items; the panel is hidden when there are no records.

Bash and Subagents each form a grouped card; tasks inside a card show only a number and status, with no nested task borders. Clicking a category title or that card's `View all` opens the corresponding category's list directly, 20 items per page, with no intermediate category menu; clicking a task row goes straight to the Bash output or the subagent status details. Keyboard users can open `O4E: View Bash tasks` or `O4E: View subagent tasks` directly from the command palette. Details are re-projected from the current synchronized records; after switching owner or when a record becomes invalid, execution links are no longer offered. Only subagent execution Sessions matching the Task, the logical owner, the Agent, and the dispatch identity can be opened proactively; Bash does not offer this navigation. There are no cancel, retry, or authorize buttons.

By default the sidebar hides validated `completed`, `failed`, and `cancelled`; Bash `interrupted/not-submitted` is also hidden once confirmed unsubmitted, with no execution claim, and stopped. `unknown`, subagent `interrupted`, cancellation-in-flight, and unverifiable records remain. Each group has at most six rows, formatted as `Bash(n)` / `Subagents(n)`, `#number · status`, `View all · (total)`. Title counts exclude hidden items, while the bottom total includes them; no empty-state or hidden-count hint is shown. Categories with no references and no anomalies are not displayed. Both the sidebar and the full list sort by number descending, no longer by status; anomalous records without a trustworthy number sort last. The full list includes all terminal states, 20 items per page, and shows stage, Agent name, command exit code, and other information.

The Bash full list opened by `View all` uses two columns: `#n command prefix…` on the left and a fixed `status · stage · exit code number` area on the right. Within a page, statuses, stages, and exit codes each align and do not move with command length; status information is no longer placed in the title, which the host may truncate. Exit codes carry no `exit` label; when the stage equals the status it is not repeated; missing fields keep their column space without showing placeholders. The width budget prioritizes the number and the right-hand information; the command prefix is truncated by terminal column width, whole graphemes, and the host title limit, and is omitted outright when fewer than 12 columns remain. Layout is recomputed when the window size changes; the sidebar still shows only number and status. Search matches the actually displayed number and command prefix on the left.

Prefixes come only from Bash Parts of the current owner that are synchronized and consistent with the task identity and the full command hash; they are omitted when not yet loaded, compacted, hidden, conflicting in origin, or when the input exceeds the processing budget, and no history is requested for the list. At most 65,536 UTF-16 code units of the command and at most 4,096 code units of the first line are processed; content after a newline is not concatenated into the prefix. Control characters, bidirectional control characters, and obvious assignment, credential-keyword, URL, or absolute-path shapes cause the whole prefix to be omitted. This heuristic check is not complete sanitization: it may over-report or under-report and cannot guarantee screen-sharing safety. Commands are not copied into the task ledger or logs, and list search uses only actually displayed text.

Clicking a Bash row shows the output captured by the original Shell card: Left/Right switches between adjacent Bash tasks, Up/Down scrolls the current output by screen, `r` refreshes, and `b` returns. Internally each segment is at most 12,000 UTF-16 code units without splitting surrogate pairs; paging up and down can browse continuously across segments. Details read, via the public SDK, only the single original message bound to the current Task, without calling the model or task-management tools. Incomplete capture, missing data, or read failures are indicated explicitly; "output" does not guarantee recovery of content the host did not save. Clicking a subagent row shows status, stage, pending permission/question counts, and the validated execution Session entry. Status information is plain text and no longer masquerades as action-less menu items. Neither hiding nor viewing implies accepting results or consuming receipts.

Subagent detail actions have a visible selection state: Up/Down selects, Enter executes, mouse clicks work, and Tab / Shift+Tab switches actions; there is no search box. Bash needs no Tab or paging menu; PageUp/PageDown are equivalent to screen scrolling and do not wrap at the ends. Esc closes, and returning to the list preserves the current task's page and selection. Short output does not stretch a large panel, and the sidebar uses a lightweight left border. The full task list pages forward/backward with Left/Right, no longer placing "previous page / next page" among the task options; Up/Down selects tasks, the host search is preserved, and there is no wraparound at the ends. Paging keys only act on the open list and are released after closing; the sidebar itself does not preempt chat input focus — the pure keyboard entry remains the command palette.

Workflow is an experimental Beta, off by default. Only after explicitly setting `"enableWorkflow": true` in `.o4e/config.jsonc` and rebuilding and restarting does a separate lightweight grouped card `Workflows(n) · Beta` and the command-palette entry `O4E: View Workflows (Beta)` appear. When off, Workflow checkpoints are not read, the area and entry are not shown, and normal Tasks are not cancelled.

The Workflow sidebar shows at most six items; normal terminal states are hidden but `View all · (total)` is retained; anomalous records are still shown. Row identity comes from a short suffix of the Run ID, expanded to the full ID on conflict — not a task number or creation order. The full list has 20 items per page, Left/Right paging, Up/Down selection, Enter for details, and Esc to close; details provide step paging, scrolling, and a visible back action, and going back preserves the list page and selection; switching owner closes the old popup. Only the current owner's allowlisted summaries are shown; inputs, outputs, reports, or evidence bodies are not read. It neither revalidates Gate evidence nor resumes or advances Runs. The model can use `o4e_workflow action:list` to discover the current Agent's Runs after authorization, then query with `read`; the UI snapshot is not a basis for tool authorization or execution.

These cards do not replace the tool cards in the chat flow and are not controlled by `enable_o4e_task_detail`: that switch only controls the body returned by `o4e_task`; the human single-line display and the model's complete bounded-return semantics remain unchanged.

The canonical ledger of new Bash tasks is stored in independent O4E SQLite; owner Session metadata retains only lightweight display summaries without creating a separate Command Session, so it does not add ordinary Session list entries or empty subagent navigation items. Historical Command Sessions are not automatically deleted or migrated. The checkmark on a native background Task tool card means the start call has returned and is insufficient proof that the Agent has finished; OpenCode 1.18.31 may still show a checkmark for queued Sessions not yet dispatched, and the public plugin interface currently cannot independently change that determination. This limitation does not mean O4E treats queued as completed.

The Task sidebar, list, and details no longer repeatedly show `Read-only · recorded snapshots`, `recorded`, or similar hints; the record source and read-only boundary are explained only here. Status updates with the host-synchronized Session metadata and does not prove live execution or result acceptance. Permission, question, retry-waiting, failure, unknown, and interrupted states are preserved; missing or unverifiable records are still marked unavailable. An old record's `running` does not prove the process is still running, and `completed` does not mean the result has been read or accepted. Confirm status and results through the native task card and the authorized `o4e_task status/watch/output` in the normal protocol.

The owner recovery copy is published after the canonical commit; after the outer operation exits the Task/transition serial region it waits for this operation's publication attempt, not for sibling task execution to finish. Publication failure neither rolls back the canonical result nor replays execution; it is surfaced as an `owner-publication-failed` diagnostic, cleared after a successful directed recovery (`ISSUE-TASK-OWNER-PUBLICATION`, covered by automated regression; real host storage failure has not been accepted). Server-side publication does not guarantee a same-frame UI refresh. Command terminal-state display checks claim and stop evidence; invalid completed records are marked anomalous rather than hidden (`ISSUE-TUI-COMMAND-CLAIM`). Display validation does not replace the Runtime's full ledger validation; confirm status with authorized task-management queries and do not modify the ledger by hand.

The sidebar calls no model, management tool, or HTTP API; it reads only the current owner's synchronized references and records, and shows no command bodies, descriptions, output, log paths, working directories, or raw errors. Only when the user actively views Bash output does it read the bound message via the host SDK and verify the caller identity; it never resumes/dispatches tasks, consumes receipts, answers interactions, scans all Sessions, or polls message history. After switching Sessions, the old owner's output is not shown, and tasks of siblings or other owners are not aggregated.

`install`, `build`, and `import` generate `.opencode/tui/opencode-for-everything/index.tsx` and register it in `.opencode/tui.json[c]`; global installation uses the corresponding global configuration directory. The entry is outside the server-auto-scanned `plugins/` directory, and the npm package provides separate `./server` and `./tui` entries. `--no-tui` only disables the installer's interactive interface, not this sidebar.

Registration preserves JSONC comments, user plugins and options, themes, keybindings, and enabled preferences, and rebuilding does not duplicate registrations. At TUI startup, the active configuration's Beta switch is read based on the public working directory and the selection rules shared with the server: an explicit `o4e_config` takes precedence, otherwise the project `.o4e/` takes precedence over the global one; when the configuration is unavailable or invalid the switch is off, and build switches from other configuration roots are not carried over. Only the selected configuration file is read — no credentials or other configuration content is read for display — and the switch is not hot-reloaded. Uninstall removes only the matching O4E registration and managed modules, preserving user TUI configuration. Installation/import failure rollback includes the TUI files and registration. `status` checks the existence of files and registration and **does not prove successful host activation**.

You can disable `opencode-for-everything.tasks` in the host Plugins panel, or set the corresponding `plugin_enabled` entry to `false`; an explicit choice in the host KV may override the configuration. Slot registration and plugin-deactivation cleanup are managed by the host.

The implementation has been checked against the OpenCode **1.18.31** public TUI documentation and the local SDK **1.18.21** interfaces; automation covers projection, build, registration, uninstall, rollback, and the npm manifest. Real interactive TUI on Linux has verified standalone TSX loading and sidebar rendering of completed Bash records under both detail configurations. **Subagent grouping and on-screen ordering with Todo, dynamic switching, deactivation, and real machines on Windows/macOS have not been visually accepted**, and compatibility with older hosts is not claimed.

A later card version verified, in an isolated Linux TUI, the Bash card, command-palette entries, task list/details, non-empty Workflow checkpoints and step paging, cross-page access with 21 Bash records, and Agent execution Session navigation. The real host CLI's dual detail modes were verified for start/begin/list/pause and result equivalence using a local fake provider; this does not equal real report Gates, the three evidence types, the full compaction/restart chain, or remote-model acceptance.

The current terminal-state filtering, pure-number ordering, and list Left/Right paging have automated projection and key-layer regression coverage; real interactive TUI visual acceptance of this change has not been completed, so the older acceptance above cannot be reused to claim it verified.

The command-prefix version was additionally verified in an isolated real TUI on Linux / OpenCode 1.18.31: full-list single-line prefix display, 21-item Left/Right paging, prefix search, and output details; prefixes shown at 72 columns, omitted when dynamically shrunk to 52 columns, and shown again after width recovery. Source validation, sensitive shapes, omission budgets, and grapheme truncation have automated regression. A complete real-machine matrix for long commands and Chinese/emoji truncation was not completed, and Windows/macOS were not verified; locally deterministic services generating real host tasks do not equal remote-model acceptance.

The above prefix real-machine checks correspond to the initial layout with the command after the status; this was later adjusted so the command immediately follows the number and the exit code shows only the number. Automated regression was added, but this final layout has not been separately re-accepted in a real TUI.

The version with an independent right-hand status column was verified in an isolated TUI on Linux / OpenCode 1.18.31 with the current components and 21 synthetic snapshots for dynamic widths of 52/72/100 columns, long and short commands, missing prefixes, success/failure/running statuses, Left/Right paging, and command-prefix search. This evidence covers only layout and interaction on the real host and does not represent command execution or lifecycle acceptance; combined-emoji glyph rendering in terminal dumps is still limited, and Windows/macOS were not verified.

There is also a completed acceptance on Linux / OpenCode 1.18.31 / real models for a single-step task-created/task-result → report Gate → read/list flow. It is CLI evidence and does not replace TUI visual, full three-evidence-type matrix, or restart acceptance.

The Workflow Beta version additionally completed, with a real-model-driven main Agent and Reviewer/Architect roles on Linux / OpenCode 1.18.31, a two-step quality-gate (task-created, task-result) and pause/resume/pause retaining the active Attempt; after restarting the final installed version, the 140-column sidebar, completed/paused lists, and step details were verified. With the default off, the ordinary Bash six-item sample test passes. Opposite global/project switches and shared-module import after installation have automated regression, but the opposite-switch real-machine matrix, 21+ Workflow cross-page navigation, dynamic owner switching, the full three-Gate matrix, and Windows/macOS were not verified in this round; narrow-screen dumps have scaling artifacts and are not used as clean screenshot evidence.
